## Release-enablement blockers

### B1 — alias/result handling is improved, but contract and real-path proof remain partial

The server/local identifier split is real, and `_doPass` now awaits
`resolvePassTeardown` (`swipe_feed.dart:112-142`). A server card no longer sends
`encounter_id` to native, and channel errors become a non-success result.

Three gaps remain:

1. `resolvePassTeardown` sends both **fresh and stale** aliases to native
   (`pass_teardown.dart:108-116`). The branch's fix note deliberately specifies
   stale attempt followed by an honest native hit/miss, so this is not itself a
   safety violation. It does, however, contradict the method/UI comments saying
   teardown occurs only through a trustworthy, still-fresh alias and leaves the
   controlling work-order contract unresolved. The test enshrines the stale
   call (`pass_teardown_test.dart:79-89`).
2. Server-card `unavailable` is not operationally observable. The only retained
   value is a field/getter on the private `_SwipeFeedState`, while the sole
   `debugPrint` excludes unavailable outcomes (`swipe_feed.dart:25-38,133-140`).
   The pure helper test can see it, but the hardware operator and committed
   evidence layer cannot.
3. The advertised “real-controller-path” Swift matrix is still mostly a helper
   reconstruction. Inbound, outbound, two-role, and live-hit tests call the
   test-local `teardown` function over `W5Ownership`; the actual
   `W5LinkController.dropPeer` and `BackgroundBeacon.dropPeerByToken` tests only
   exercise empty-controller misses (`W5TeardownTests.swift:28-34,55-97,112-138`).
   There is also no widget/platform-channel test executing the actual `_doPass`
   path.

Required correction: settle and document fresh-only versus best-effort stale
semantics against the controlling contract; emit a sanitized diag-only result
for fresh/stale/server/native-unavailable outcomes; and introduce a controller
test seam that drives real hit paths and a widget or integration test that
drives `_doPass` through the channel boundary.

### B2 — the event layer still cannot prove the required hardware chains

The vocabulary now has many reachable emits, but presence is not correct
placement. Concrete gaps:

- `coldLaunch` is emitted in `bootFromPersistence` **before** `ensureManagers`
  creates the CoreBluetooth managers (`BackgroundBeacon.swift:257-273`). A
  `willRestoreState` callback therefore cannot be the first relevant event in a
  new launch epoch as Case 3 requires; every genuine restoration is first
  labelled `coldLaunch`.
- `restoreRebind` is emitted only for the forced-rebuild failure path. Normal
  successful recovery of both notify characteristics produces no structured
  rebind result (`BackgroundBeacon.swift:833-880`).
- The advertised-token dial emits `dialStart`, but the locked-iOS/no-token path
  calls `central.connect` without one (`BackgroundBeacon.swift:1106-1113,
  1147-1173`).
- Normal physical disconnect invokes `W5LinkController.linkDown` and enters
  grace without emitting `.linkDown`; that event name is used later only when an
  ownership lease ends (`W5LinkController.swift:342-365,831-875`). Case 2 cannot
  independently prove physical drop from the requested event.
- The inbound HELLO_ACK send, outbound/inbound protocol-violation rejection, and
  outbound rejection send do not have complete role-correct structured events.
  The hold-side tiebreak event also says only `hold`, not whether the reason was
  a live keeper, cap, or another decision.
- The Dart/native fault methods exist, but no production diagnostic UI, launch
  control, or other committed app call invokes `BeaconService.armW5Fault`.
  Outside tests it is dead code, so an installed release-mode diag artifact has
  no committed way to select and arm Case 1. The API additionally permits and
  tests a wildcard “next peer” hook, contrary to the selected-peer/no-broad-stale
  requirement (`W5Diag.swift:85-100`, `w5_diag_control_test.dart:30-41`).
- Every diag build also carries a hard-coded four-second HELLO delay for every
  outbound dial, rather than a selected, one-shot perturbation
  (`BackgroundBeacon.swift:135-142`, `W5LinkController.swift:262-275`). It can
  confound every matrix case even when the targeted fault is not armed.
- Sensitive emit call sites are not themselves `#if INRANGE_DIAG` guarded. The
  no-op body plus `@autoclosure` is useful, but it is not the two independent
  layers expressly required by work-order lines 148–153.

Required correction: provide a diag-only operator control that requires a
validated selected peer, returns an armed handle/status, expires automatically,
and has no wildcard; emit at each actual state transition above; derive the
launch classification from restoration launch context/callbacks rather than
pre-labelling every launch cold; and compile-gate sensitive call sites.

### B3 — the run-secret implementation directly breaks the safety contract

The work order requires one random ephemeral fleet secret that is never
persisted or printed and is destroyed after sanitization. The implementation
instead:

- stores provisioned and generated secrets in a UserDefaults suite
  (`W5Diag.swift:74-82,119-160`);
- commits a fixed launch/test value in the shared Xcode scheme
  (`diag.xcscheme:70-104`);
- bakes a generated value into the diag artifact and prints it to build output
  (`build_diag_artifact.sh:25-46`); and
- leaves a header comment claiming the secret lives only in memory and is never
  persisted or printed (`W5Diag.swift:15-17`).

The artifact path also starts native before making an unawaited Dart-to-native
provisioning call (`beacon_service.dart:1018-1023`). The static `runSecret` is
resolved once, so first-use ordering must be proven rather than asserted. The
injection test skips instead of failing if its environment is missing
(`W5DiagTests.swift:60-72`), while another test affirmatively locks in plaintext
persistence (`:75-87`).

Restoration continuity and a never-persisted key are in tension, but that does
not authorize silently replacing the requirement. Required correction: stop
printing/baking/committing the key and obtain an explicit owner decision. Either
implement an ephemeral design with a sanitized restoration bridge, or document
and approve narrowly scoped transient storage with protection, backup policy,
expiry, deletion, and fail-closed tests. Do not proceed with the current
plaintext UserDefaults design.

### B4 — the shared primitive still cannot guarantee locked, ordered evidence

`W5EvidenceWriter` fixes the overwrite-on-open-failure bug, but the mandatory
preflight still lacks a trustworthy logger:

- Each append opens and closes an existing file while applying
  `completeUnlessOpen` (`W5EvidenceWriter.swift:42-103`). Once the phone is
  locked, an already-closed protected file cannot be reopened; expected
  locked-state events become counted drops rather than evidence. The code did
  not repair the structural issue identified in the previous review.
- Event sequence allocation and file append use separate locks
  (`W5Diag.swift:53-70,196-209`). Two threads can receive sequence 1 and 2, then
  acquire the writer lock in reverse order, leaving non-monotonic file order.
- RSSI cap trimming replaces the file directly outside the writer, ignores write
  failure, resets offsets, and does not reapply protection or backup exclusion
  (`W5LinkController.swift:942-955`). RSSI drain/ack deletion is likewise outside
  the purported one primitive (`:958-989`).
- The committed extraction script never pulls `w5_events.jsonl` or either
  rotated `.1` evidence file (`hw_matrix_pull.sh:19-27`). As written, the
  preflight cannot produce the primary event artifact it is supposed to
  validate.
- Rotation, protection, backup-exclusion, and deletion errors use `try?` without
  incrementing any family counter (`W5EvidenceWriter.swift:105-125`). These are
  silent integrity failures despite the checkpoint's “after every op” claim.
- Simulator tests conditionally assert attributes only when reported and do not
  test locked-device writes, concurrency/order, attribute failure, rotation
  failure, or the direct RSSI replacement path (`W5DiagTests.swift:129-193`).

Required correction: serialize sequence assignment and write in one queue or
critical section; use a locked-state-capable handle/lifecycle consistent with the
approved protection class; route every append/trim/replace/rotate/delete through
the hardened primitive; account every failed integrity operation; and add
concurrency plus real-device lock/rotation assertions before preflight approval.

### B5 — the CI wiring is broader, but its negative contract is intentionally weaker

The workflow now runs both schemes, adds an isolation job, and gates `build-ios`
on both jobs. That is meaningful progress. It does not implement the specified
negative control:

- `check_final_binary_isolation.sh` explicitly allows diagnostic filenames and
  the `armW5Fault`/`setDiagRunSecret` controls in production and reports them only
  informationally (`:5-18,27-57`). Work-order lines 238–242 require production
  to contain none of the event names, evidence filenames, hooks, or run-secret
  configuration keys.
- The checker enforces only `W5Diag`/`W5EvidenceWriter` symbols and one environment
  key. It does not check event strings, all evidence filenames/control strings,
  or whether W5 link-layer symbols/code survive the production artifact.
- The iOS workflow does not run automatically on pushes to this implementation
  branch; manual run `30919718754` was required to obtain exact-SHA evidence.
- That run passed both native suites but failed `isolation-ios` at `FAIL: prod
  build`; the release artifact was skipped. Both isolation builds omit
  `--no-codesign`, unlike every other clean-runner device build in the workflow,
  making signing the leading source-level cause. The script suppresses all
  Flutter build output, so its own CI log hides the precise failure. Either way,
  B5 is empirically red and neither binary assertion executed.

Required correction: first resolve the apparent conflict between production
foreign-wipe machinery and the stricter work-order binary contract with the
owner; then enforce the agreed list rather than printing it, include a positive
control for every discriminator, make the builds explicitly unsigned, and keep
the exact-SHA workflow green.
